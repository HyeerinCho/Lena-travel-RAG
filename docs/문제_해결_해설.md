# 겪었던 문제와 해결 — 쉬운 해설

대학교 2학년 기준으로, README의 「겪었던 문제와 해결」 중 아래 네 가지를  
**왜 문제였고 → 어떻게 고쳤고 → 왜 그렇게 했는지** 쉽게 정리한 문서입니다.

관련 파일: `src/config.py`, `src/travel/tour_api/_client.py`,  
`src/travel/tour_enrich.py`, `src/travel/travel_realtime.py`,  
`src/travel/travel_agent.py`, `src/travel/travel_graph.py`, `src/prompts.py`

## 1. TourAPI Encoding 키 → 이중 인코딩

| 항목 | 내용 |
|------|------|
| 문제 | TourAPI Encoding 키 사용 시 이중 인코딩 |
| 원인 | `urlencode`가 다시 인코딩 |
| 해결 | data.go.kr **「일반 인증키(Decoding)」** 값 사용하도록 통일 |
| 파일 | `src/config.py`, `src/travel/tour_api/_client.py` |

### 쉬운 비유

비밀번호에 특수문자 `@`가 있는데,

1. 사이트가 이미 `@`를 `%40`으로 바꿔준 키를 줌 (**Encoding 키**)
2. 우리 코드가 URL 만들 때 **또** `@ → %40`으로 바꿈

그러면 `@`가 `%2540`처럼 이상하게 변해서, 서버가 “인증키 틀림”이라고 거부합니다.

### 왜 생기나

data.go.kr는 인증키를 두 종류로 줍니다.

| 종류 | 의미 | 예시 |
|------|------|------|
| **Decoding 키** | 원본 키 | `abcd/efg==` |
| **Encoding 키** | URL용으로 이미 변환된 키 | `abcd%2Fefg%3D%3D` |

우리 코드는 URL을 만들 때 `urllib.parse.urlencode()`를 씁니다.

```python
url = f"{base_url}/{operation}?{urllib.parse.urlencode(query)}"
```

`urlencode`는 특수문자를 **자동으로** 인코딩합니다.  
그래서 Encoding 키를 넣으면 **두 번** 인코딩됩니다.

### 해결

`.env`에는 **Decoding 키만** 넣도록 통일했습니다.  
`config.py` 주석에도 그 이유를 적어 두었고, `_client.py`에서도 Decoding 키를 쓰라고 안내합니다.

> **한 줄 요약:** URL 인코딩은 코드가 하니까, 키는 원본(Decoding)을 넣어야 한다.

## 2. 외부 API 실패해도 챗봇이 죽지 않게 (장애 격리)

| 항목 | 내용 |
|------|------|
| 문제 | 외부 API 실패 시 챗봇 전체 중단 우려 |
| 원인 | TourAPI/날씨 호출이 답변 경로에 결합 |
| 해결 | 실패해도 빈 컨텍스트 반환 → 기본 동작 유지 |
| 파일 | `src/travel/tour_enrich.py`, `src/travel/travel_realtime.py` |

### 쉬운 비유

식당에서 메인 요리(일정 추천)는 정상인데,  
사이드 메뉴(날씨, 반려동물 정보)만 배달이 안 왔다고 가게 전체를 닫으면 안 됩니다.

사이드가 없으면 “없음”으로 두고, 메인은 그대로 내보내는 게 맞습니다.

### 왜 위험했나

여행 답변 흐름에 TourAPI·날씨가 붙어 있습니다.

```
검색 → (TourAPI 보강) → (날씨 조회) → LLM 일정 생성
```

여기서 TourAPI/날씨 오류를 그대로 올리면,  
**외부 API 하나가 죽어도 전체 챗봇이 500 에러**가 납니다.

### 해결

외부 호출을 `try/except`로 감싸고, 실패하면 **빈 결과**를 반환합니다.

- `tour_enrich.py`: TourAPI 실패 → `[]` 또는 `{}`
- `travel_realtime.py`: 날씨 실패 → `[]` / 빈 컨텍스트

그러면 LLM은 그냥 내부 DB(SQLite+FAISS) 정보만으로 일정을 만듭니다.  
날씨·반려동물 보강만 빠질 뿐, 기본 기능은 살아 있습니다.

> **한 줄 요약:** 부가 기능은 실패해도 “없음”으로 처리하고, 핵심 답변은 계속 만든다.  
> 이런 설계를 **장애 격리(fault isolation)** / **graceful degradation**이라고 합니다.

## 3. import할 때마다 그래프/인덱스 초기화 → lazy init

| 항목 | 내용 |
|------|------|
| 문제 | import 시마다 그래프/인덱스 초기화 |
| 원인 | 모듈 레벨 초기화 |
| 해결 | `@lru_cache` + `get_travel_agent()`로 lazy init |
| 파일 | `src/travel/travel_agent.py` |

### 쉬운 비유

카페에 손님이 올 때마다  
원두 갈고, 머신 예열하고, 메뉴판 인쇄를 다시 하면 너무 느립니다.

한 번만 준비해 두고, 손님마다 **이미 준비된 머신**을 쓰는 게 맞습니다.

### 왜 문제였나

Python에서 모듈을 import하면, 파일 맨 위 코드가 바로 실행됩니다.

만약 그 시점에

- FAISS 로드
- DB 연결
- LangGraph 컴파일

을 해버리면, CLI/API가 뜰 때마다(또는 import할 때마다) 무거운 초기화가 반복됩니다.

### 해결

`@lru_cache` + `get_travel_agent()`로 **필요할 때 한 번만** 만듭니다.

```python
@lru_cache
def get_travel_agent():
    search = TravelSearchService()
    return build_travel_graph(search)
```

동작 방식:

1. 첫 `ask_travel()` 호출 → 그래프 생성 후 캐시에 저장
2. 두 번째 이후 → 캐시된 그래프 재사용

이걸 **lazy initialization(지연 초기화)** 이라고 합니다.  
“시작할 때 미리”가 아니라 “처음 쓸 때” 준비하는 방식입니다.

> **한 줄 요약:** 무거운 준비는 한 번만, 그다음부터는 재사용한다.

## 4. 질문 유형 무시하고 항상 일정만 생성 → intent 라우팅

| 항목 | 내용 |
|------|------|
| 문제 | 질문 유형 무시하고 항상 일정만 생성 |
| 원인 | 단일 프롬프트 |
| 해결 | 의도(intent) 라우팅으로 `city_list` / `qa` / `rewrite_day` / `multi_itinerary` / `itinerary` 분기 |
| 파일 | `src/travel/travel_graph.py`, `src/prompts.py` |

### 쉬운 비유

친구가

- “제주 어디가 좋아?”
- “성산일출봉 몇 시에 열어?”
- “2일차만 바꿔줘”
- “일정 3개 짜줘”

라고 물어보는데, 매번 “자, 2박3일 일정표입니다!”만 주면 불편합니다.

질문 종류를 먼저 분류하고, 그에 맞는 답변 방식을 골라야 합니다.

### 왜 문제였나

처음에는 프롬프트가 사실상 **일정 생성용 하나**였습니다.  
그래서 단순 질문도 억지로 일정표처럼 나왔습니다.

### 해결

질문을 **intent(의도)** 로 나눈 뒤, 프롬프트를 분기합니다.

| intent | 언제 | 하는 일 |
|--------|------|---------|
| `city_list` | “어디가 좋아?” | 도시/장소 목록 추천 |
| `qa` | “몇 시 열어?” 같은 단순 질문 | 짧게 답변 |
| `rewrite_day` | “2일차만 바꿔줘” | 기존 일정 중 하루만 수정 |
| `multi_itinerary` | “일정 3개 짜줘” | 여러 안 제시 |
| `itinerary` | 기본 | 일반 일정 생성 |

우선순위 예시는 이런 식입니다.

```python
def _resolve_intent(...):
    if "city_list" in intents:
        return "city_list"
    if count:
        return "multi_itinerary"
    # ...
    if "qa" in intents:
        return "qa"
    return "itinerary"
```

그리고 `prompts.py`에 의도별 프롬프트 6종이 있고,  
그래프의 `build_itinerary` 노드가 intent에 맞는 프롬프트를 골라 Gemini에 보냅니다.

> **한 줄 요약:** 먼저 “사용자가 뭘 원하는지” 분류하고, 그에 맞는 답변 템플릿을 쓴다.  
> 이게 **intent routing(의도 라우팅)** 입니다.

## 네 개를 한눈에

```
1) 인증키     → Encoding을 또 인코딩하면 깨짐 → Decoding 키만 사용
2) 외부 API   → 실패해도 전체 중단 금지 → 빈 값으로 넘어가기
3) 초기화     → import마다 무거움 → 처음 쓸 때 1번만 (@lru_cache)
4) 답변 방식  → 전부 일정표 X → 질문 의도별로 프롬프트 분기
```

### 회고용 한 문단

TourAPI 키는 코드의 `urlencode`와 충돌하지 않도록 Decoding 키로 통일했고,  
외부 API는 실패해도 빈 컨텍스트로 넘어가 핵심 RAG 경로를 지키도록 했다.  
그래프는 lazy init으로 재사용하고, 질문 intent에 따라 프롬프트를 분기해  
단순 질문·도시 추천·일정 재작성·다중 일정을 구분해서 응답한다.
