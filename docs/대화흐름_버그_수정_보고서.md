## 0. 문제의 공통 원인

9개 항목을 뜯어보면 원인이 두 곳에 몰려 있었다.

1. **의도 판별 라우팅** (`src/travel/travel_graph.py`) — 사용자 메시지가 "새 일정 만들기"인지 "이 일정만 고쳐줘"인지를 정규식 휴리스틱과 LLM 추출 결과를 섞어서 판정하는 코드(`_run_extract`, `_resolve_intent`, 각종 `_detect_*`)가 있는데, 이 판정이 어긋나면 사용자 입장에서는 "말을 무시한다" 혹은 "엉뚱하게 처음부터 다시 짠다"로 보인다. 9개 문제 중 6개가 여기서 비롯됐다.
2. **날짜 처리** (`src/travel/travel_realtime.py`) — 날씨/휴무 정보가 여행 실제 날짜가 아니라 서버의 "지금 이 순간"을 기준으로 계산되고 있었다.

아래는 이 두 원인이 각 문제로 어떻게 이어졌는지, 그리고 무엇을 어떻게 고쳤는지를 항목별로 정리한 것이다.

## 1단계 — 대화 흐름 핵심 버그

### 1-A. 날씨 날짜가 일정과 안 맞음

| | 내용 |
|---|---|
| **문제** | 미래 날짜로 여행을 잡아도 "휴무 추정" 안내가 실제 여행일이 아니라 서버가 응답을 만드는 시점의 요일을 기준으로 계산됨 |
| **원인 파일** | `travel_realtime.py:292-331`, `travel_graph.py`(`_heuristic_start_date`) |

**Before**
```python
# build_realtime_context() 안에서 — 항상 "지금"(now) 기준
closed_today = operating_notes(places, when=now)
...
lines.append(f"[오늘({_WEEKDAY_KO[now.weekday()]}) 휴무 추정]")
```
출발일 추출도 `YYYY-MM-DD`, `M월 D일`, "내일/모레"만 인식했고, 그 외("다음주 금요일부터", "이번 주말" 등)는 조용히 "오늘 출발"로 간주됐다.

**After**
```python
def operating_notes_by_day(places, *, trip_start, num_days, limit=12):
    """Day1..N 각각의 실제 날짜로 휴무 추정을 계산한다."""
    out = []
    for day_index in range(1, num_days + 1):
        target = trip_start + timedelta(days=day_index - 1)
        notes = operating_notes(places, when=target, limit=limit)
        if notes:
            out.append({"day": day_index, "date": ..., "weekday": ..., "places": notes})
    return out
```
- 날씨 텍스트에 Day별로 "휴무 추정(요일)"을 붙여 프롬프트에 전달하도록 변경
- `_heuristic_start_date`에 요일명/"다음주"/"이번 주말" 등 상대 날짜 패턴 추가
- `TRAVEL_EXTRACT_PROMPT`에 `{today}`(현재 날짜)를 명시적으로 넘겨 LLM이 상대 날짜를 정확히 계산하도록 함
- 출발일을 끝내 못 정하면 조용히 "오늘"로 넘기지 않고, 응답에 경고 문구를 추가

**검증** (실서버, 출발일 미지정 상태로 "제주 3일 일정 짜줘")
```
realtime weather: [(1, '2026-08-07', '금'), (2, '2026-08-08', '토'), (3, '2026-08-09', '일')]
warnings: ['출발일을 알려주지 않아 오늘부터 시작한다고 가정하고 날씨를 보여드려요.
            정확한 날짜를 알려주시면 다시 맞춰드릴게요.', ...]
```
→ 날짜/요일이 정확히 계산되고, 가정한 상태임을 사용자에게 명시적으로 알림.

### 1-B. 같은 장소를 두 번 이상 추천함

| | 내용 |
|---|---|
| **문제** | 재추천 방지 장치(제외 목록, 중복 제거)가 이미 있는데도 같은 장소가 반복 등장 |
| **원인 파일** | `travel_graph.py` `_search_for_state` |

**Before**
```python
if state.get("want_alternatives") or state.get("intent") == "place_list":
    pass  # keep shown in filter
elif state.get("intent") == "itinerary" and not state.get("rewrite_day"):
    # 이 elif 블록 안에서는 want_alternatives가 항상 False로 확정된 상태(위 if가 이미 걸러냄)
    shown_ids = [] if not state.get("want_alternatives") else shown_ids  # → 항상 []
    shown_names = [] if not state.get("want_alternatives") else shown_names  # → 항상 []
```
`elif` 안에서 `want_alternatives`는 위의 `if`가 이미 True 케이스를 다 가져갔기 때문에 도달 시점에 **항상 False**다. 즉 이 조건문은 사실상 `shown_ids = []`, `shown_names = []`를 무조건 실행하는 죽은 분기였다. 새로 "일정 만들어줘" 요청이 올 때마다 지금까지 보여준 장소 목록이 통째로 리셋되어, 다음 추천에서 같은 장소가 다시 나올 수 있었다.

**After**
```python
# 세션 내에서 한 번 보여준 장소는 계속 제외 후보로 유지한다(재추천 방지).
# 단, 이번 세션에서 아직 아무 일정도 만든 적이 없는 "첫 일정" 요청이면
# (previous_itinerary가 없으면) 과거 다른 대화의 shown 목록에 얽매이지 않도록 초기화한다.
if (
    state.get("intent") == "itinerary"
    and not state.get("rewrite_day")
    and not state.get("want_alternatives")
    and not state.get("previous_itinerary")
):
    shown_ids = []
    shown_names = []
```
"세션에 만든 일정이 하나도 없을 때"만 리셋하고, 그 외에는 계속 누적한다.

### 1-C. "이 날만 다시" 클릭 시 대안 확정 방식

| | 내용 |
|---|---|
| **문제** | 대안 카드를 클릭해도 실제로 그 구성대로 반영되는지 불확실 |
| **원인 파일** | `travel_graph.py`(`_merge_day_into_itinerary`), `src/front/index.html`(`renderDayOptions`) |

**Before**
- `TRAVEL_REWRITE_DAY_PROMPT`는 이미 대안을 최대 3개까지 만들어 `day_options`로 반환하고 있었음(문제 없음)
- 하지만 사용자가 대안 버튼을 클릭하면, 이미 구조화된 데이터(`slots`)가 있는데도 그걸 버리고 `"3일차를 다음으로 확정해줘: A, B, C"` 같은 **자연어 문장**을 새로 만들어 전체 의도 판별 파이프라인에 다시 태웠다. 장소 이름만으로 정확한 시간대·순서를 되짚어야 해서 깨지기 쉬운 경로였다.

**After** — 구조화된 필드를 신설해 자연어 재해석 없이 직접 반영

```python
# travel_agent.py
def _apply_confirm_day(session, previous_itinerary, confirm_day):

    day_num = int(confirm_day.get("day"))
    slots = confirm_day.get("slots")
    new_day = {"day": day_num, "theme": confirm_day.get("theme") or "", "slots": slots}
    itinerary = _dedupe_itinerary_slots(_merge_day_into_itinerary(previous_itinerary, day_num, new_day))
    ...
```
```javascript
// index.html — rewriteDay()가 { rewrite_day: day }를 구조화 필드로 보내는 것과 동일한 방식
async function confirmDayOption(day, opt) {
  await runStreamQuery(question, {
    confirm_day: { day, theme: opt.theme || "", slots: opt.slots || [] },
  });

```
`api.py`의 `TravelQueryRequest`에 `confirm_day` 필드를 추가하고, `/query`·`/query/stream` 두 엔드포인트 모두에 배관 연결. `ask_travel_in_session`/`stream_travel_in_session`이 `confirm_day`가 오면 LLM 호출 없이 바로 반영 후 리턴.

### 1-D. 하루만 추천받은 상태에서 "다른 곳 없어?" → 전체가 리셋됨

이번 세션에서 **가장 손이 많이 간 항목**이고, 고치는 과정에서 새로운 버그를 하나 더 발견했다.

| | 내용 |
|---|---|
| **문제** | "1일차만 바꿔줘" 이후 "다른 곳 없어?"라고만 물으면 전체 일정이 새로 만들어지며 처음과 비슷/동일해짐 |
| **원인 파일** | `travel_graph.py` `_resolve_intent`, `_heuristic_extract` |

**원인 1 — 라우팅에 "지금 대화가 어느 날짜를 다루고 있었는지" 기억이 없음**

`_resolve_intent`의 우선순위 캐스케이드(`meta > city_list > place_list > count > edit > rewrite_day > qa > itinerary`)에는 "다른 곳 없어?"(`want_alternatives`) 자체를 처리하는 분기가 없었다. 일차 번호를 명시하지 않으면 `rewrite_day`도 안 잡히고 기본값인 "새 일정 통째로 생성"으로 떨어졌다.

**Before**
```python
# _resolve_intent — want_alternatives를 아예 고려하지 않음
if "edit" in intents and has_previous: return "edit"
if rewrite_day is not None: return "itinerary"
if "qa" in intents: return "qa"
return "itinerary"  # ← "다른 곳 없어?"가 여기로 떨어짐 = 전체 재생성
```

**After 1 — 세션에 "마지막으로 손댄 일차" 기억을 추가**
```python
# session_store.py — sessions 테이블에 last_target_day 컬럼 추가
# travel_agent.py
def _next_last_target_day(result):
    if result.get("rewrite_day"): return int(result["rewrite_day"])
    if result.get("intent") == "edit" and result.get("target_day"): return int(result["target_day"])
    if result.get("intent") == "itinerary" and not result.get("rewrite_day"): return 0  # 전체 새 일정 → 초기화
    return None  # 일정과 무관한 턴 → 유지
```
```python
# travel_graph.py _run_extract
if (
    merged["want_alternatives"] and previous
    and merged.get("rewrite_day") is None
    and not (merged.get("insert_place") and merged.get("target_day"))
    and state.get("last_target_day")
):
    merged["rewrite_day"] = state["last_target_day"]
```

**원인 2 — 테스트 중 발견: "다른 곳"이라는 표현 자체가 place_list 패턴과 겹침**

수정 후 실행해보니 `rewrite_day`는 정확히 2로 잡히는데 최종 `intent`가 계속 `place_list`로 나왔다. 추적해보니 `_heuristic_extract` 내부의 다른 코드가 원인이었다.

```python
# _heuristic_extract (Before)
elif _detect_place_list_intent(query) or _detect_want_alternatives(query):
    intent = "place_list"
```
그리고 `_detect_place_list_intent`의 패턴 중 `r"다른\s*(곳|장소|데)"`가 "다른 곳 없어?"와 직접 매치되어, `previous_itinerary` 존재 여부와 무관하게 `base["intent"]`가 `"place_list"`로 고정되고 있었다. 이건 `_resolve_intent` 캐스케이드에서 `place_list`가 `rewrite_day`보다 우선순위가 높기 때문에, 내가 추가한 `rewrite_day` 로직을 통째로 무력화시키고 있었다.

**After 2**
```python
# _heuristic_extract — want_alternatives만으로는 여기서 place_list로 단정하지 않음
elif _detect_place_list_intent(query):
    intent = "place_list"
...
else:
    intent = "itinerary"  # 이전 일정 존재 여부는 여기서 알 수 없으므로 _run_extract에 맡김
```
```python
# _run_extract — 이전 일정이 있으면 place_list가 아니라 그 일정의 연장으로 처리
if previous and merged.get("want_alternatives") and merged.get("intent") == "place_list":
    merged["intent"] = "itinerary"
```

**검증** (실서버, 세션 하나로 연속 대화)
```
Q2 "1일차만 바꿔줘" → Day1: [] (재작성됨, 나머지 유지)
Q3 "다른 곳 없어?"  → intent: itinerary, rewrite_day: 1
                     Day1: ['관덕정']   ← 새 장소로 갱신
                     Day2: ['다이나믹메이즈 제주']  ← 그대로 유지
                     Day3: [] ← 그대로 유지
```
Day 2/3는 건드리지 않고 Day 1만 이어서 다시 짰다 — 의도한 동작.

### 1-E. "일정 속 OO 싫어해" 무시됨

| | 내용 |
|---|---|
| **문제** | 정형화되지 않은 문구로 특정 장소를 싫어한다고 말하면 반영되지 않고 원래 답 그대로 나옴 |
| **원인 파일** | `travel_graph.py` — 정규식 휴리스틱과 LLM 추출이 "제외 장소 목록"에는 넣지만, 그것을 "edit로 라우팅"하는 조건은 정규식 매칭에만 의존 |

**Before**
```python
if previous and _heuristic_exclude_places(state["query"]) and not _detect_edit_intent(state["query"], previous):
    if not merged.get("rewrite_day"):
        base["intent"] = "edit"
```
정규식이 못 잡는 표현(어미 변형 등)이면, LLM이 `exclude_places` 필드는 제대로 뽑아내도 **intent가 edit로 안 잡혀서** 실제로는 아무것도 빠지지 않았다.

**After**
```python
# 정규식/LLM 둘 중 하나라도 이번 턴에 제외 장소를 잡아냈고,
# 그 이름이 실제로 기존 일정 안에 있으면 — 문구가 정형화되지 않아도 — 반드시 edit로 라우팅
this_turn_excludes = _merge_lists(base.get("exclude_places"), parsed.get("exclude_places"))
if previous and this_turn_excludes and merged.get("intent") not in ("meta", "city_list"):
    _, itinerary_names = _places_from_itinerary(previous)
    if any(_norm_name(x) in _norm_name(n) or _norm_name(n) in _norm_name(x)
           for x in this_turn_excludes for n in itinerary_names):
        merged["intent"] = "edit"
```
판단 기준을 "정규식이 매칭했는가"에서 "실제로 그 이름이 지금 일정 안에 있는가"로 바꿔, 텍스트 표현과 무관하게 확실하게 반영되도록 함.

**검증**
```
Q4 "관덕정 싫어해" → intent: edit
   answer: "Day 1 일정이 다음과 같이 변경되었습니다. - 오전: 요청에 따라 관덕정을 제거했으며..."
   Day1: []  (관덕정 제거 확인)
```

### 1-F. "~을 N일차에 넣어줘" 삽입 실패

| | 내용 |
|---|---|
| **문제** | 방금 추천받은 장소를 특정 일차에 넣어달라고 하면 반영되지 않음 |
| **원인 파일** | `travel_graph.py` `_search_for_state`, `_build_response`(edit 분기) |

**Before**
- `_search_for_state`는 `intent == "edit"`일 때 `shown_poi_ids`/`shown_place_names` 제외 목록을 리셋하지 않았다.
- 방금 추천받은 장소는 그 추천 자체 때문에 이미 `shown_*` 목록에 들어 있는 상태 → 이번 턴의 후보 검색에서 **그 장소가 먼저 걸러져 사라짐**
- 삽입 로직이 후보 풀에서 못 찾으면, 폴백 검색까지 실패할 경우 아무 안내 없이 이전 일정을 그대로 반환

**After**
```python
# "~을 N일차에 넣어줘": 넣으려는 그 장소는 이미 이전 턴에 보여줬기 때문에
# shown/exclude 목록에 걸려 후보 풀에서 사라지기 쉽다. 삽입 대상만 예외로 둔다.
insert_place = state.get("insert_place")
if insert_place:
    needle = _norm_name(insert_place)
    exclude_places = [n for n in exclude_places if ...]  # insert_place 이름만 제외 목록에서 빼줌
    shown_names = [n for n in shown_names if ...]
    shown_ids = []  # poi_id는 검색 전엔 몰라 이름으로만 걸러낼 수 있어, 이번 검색만 통째로 열어둠
```
그리고 그래도 못 찾으면(오타 등) 조용히 무시하지 않고 명시적으로 알림:
```python
return {
    "itinerary": previous,
    "answer": f"'{insert_place}'을(를) 찾지 못해 {int(target_day)}일차에 넣지 못했어요. "
              "정확한 장소명으로 다시 말씀해 주시겠어요?",
    ...
}
```

## 3단계 — 세션(유저별 분리) 버그

| | 내용 |
|---|---|
| **문제** | (실제로는 이미 브라우저 클라이언트ID 기반 분리가 구현되어 있었음. 다만 자동 소유권 이전 로직에 실질적 유출 가능성이 있었음) |
| **원인 파일** | `session_store.py` `list_sessions`, `ensure_owner` |

**Before**
```python
# 소유자가 없는(owner_id NULL) 세션은 메시지 유무와 무관하게
# "먼저 목록을 조회하거나 먼저 그 ID로 접근한 클라이언트"에게 그냥 넘어감
if item.get("owner_id") is None:
    conn.execute("UPDATE sessions SET owner_id = ? WHERE id = ? AND owner_id IS NULL", (owner_id, item["id"]))
```
실제 대화 기록이 있는 세션이라도 소유자가 비어 있다면(레거시 데이터, 경쟁 상태 등) 무조건 자동 귀속됐다 — 세션 ID를 알기만 하면(또는 우연히 먼저 목록을 조회하면) 남의 대화를 가져갈 수 있는 경로.

**After**
```python

# 자동 클레임하지 않는다. 메시지가 0개인(사실상 빈) 세션에 한해서만 자동 귀속.
if item.get("owner_id") is None and item["message_count"] == 0:
    ...
```
`list_sessions`, `ensure_owner`(단건 조회/조작 시 호출되는 공통 게이트) 양쪽 모두 동일하게 적용.

**검증** (클라이언트A가 메시지 있는 세션 생성 후, 서로 다른 클라이언트B로 접근)

## 4단계 — 자기소개(메타 질문) 속도/정확도

| | 내용 |
|---|---|
| **문제** | "이게 뭐하는 모델/건데?" 같은 질문에 응답이 느리고, 종종 장소·일정을 만들려는 것처럼 엉뚱하게 반응 |
| **원인 파일** | `travel_graph.py` `_run_extract`, `_detect_meta_intent` |

**원인 1 — 속도**: 메타 질문이어도 매 턴 무조건 `TRAVEL_EXTRACT_PROMPT` LLM 호출(요구사항 추출)을 먼저 거친 뒤에야 정규식 기반 메타 판별이 개입해 `TRAVEL_META_PROMPT`를 또 호출 — LLM 왕복 2회.

**원인 2 — 정확도**: `_detect_meta_intent` 정규식이 자연스러운 변형 표현을 놓침. 예: `이\s*(서비스|앱|봇|모델|건)`은 "이"와 "앱" 사이에 다른 글자가 끼면(`이거 어떻게 쓰는 앱이야?`) 매치되지 않았고, `어떻게\s*써`는 "쓰는" 어형을 못 잡았다. 이 경우 메타 판별에 실패해 일정 생성 경로로 새어 들어가 느리고 엉뚱한 답이 나왔다.

**After**
```python
# _run_extract 맨 앞 — 확신도 높은 정규식이면 무거운 추출 LLM 호출을 아예 건너뜀
if _detect_meta_intent(state["query"]):
    merged = {**base, "intent": "meta", "want_alternatives": False, ...}
    return merged  # TRAVEL_EXTRACT_PROMPT 호출 없이 바로 리턴 → 이후 TRAVEL_META_PROMPT 1회만 호출
```
```python
# _detect_meta_intent 패턴 확장
r"이(거|건|게)?\s*.{0,6}(서비스|앱|봇|채팅|챗봇|모델|프로그램|건)",  # 사이에 다른 말이 껴도 매칭
r"어떻게\s*(써|쓰는|사용|이용)|사용\s*법|이용\s*법|사용\s*방법",
```

**검증** (실서버)
```
Q: "이거 어떻게 쓰는 앱이야?"  (수정 전 정규식으로는 미매칭 → 일정 생성 경로로 샜을 문구)
→ intent: meta
→ answer: "안녕하세요! 저는 LENA입니다. 한국 여행 장소와 일정을 추천해 드리는 어시스턴트예요...
           날씨를 반영한 추천도 가능하니, 언제든 편하게 말씀해주세요!"
→ 응답 시간 ~4.7초 (LLM 호출 1회로 단축)
```

## 아직 남아있을 수 있는 리스크 (참고용)

- 1-D의 "전체 대안 재구성(구조 유지, 장소만 교체)" 경로는 프롬프트 지시 추가로 처리했는데, `last_target_day`가 없는 상태에서 "다른 곳 없어?"가 여러 번 반복되면 LLM이 매번 완전히 다른 조합을 낼 가능성은 남아 있음 — 실사용 중 재발하면 이 경로부터 확인
- `_norm_name` 기반 이름 부분일치는 제외/삽입 로직 전반에서 여전히 사용 중 — 매우 유사한 이름(예: "OO공원" vs "OO어린이공원")이 섞여 있는 지역에서는 오탐 가능성이 이론적으로 남아있음(이번 회귀 대상은 아니었음)
